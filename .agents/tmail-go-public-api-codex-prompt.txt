6. API KEY: ATURAN VALIDASI
================================================================================

API key harus dibaca dari MongoDB yang sama dengan TMail.

Gunakan model data yang konsisten dengan implementasi admin API key yang sudah ada di repo:

Field penting:
- name
- key
- isActive
- whitelistIps
- blacklistIps
- lastUsedAt
- lastUsedIp
- useCount
- createdAt
- updatedAt

Aturan validasi API key:

1. Cari document Mongo berdasarkan field key yang persis sama.
2. API key wajib aktif: isActive == true.
3. API key ini unlimited, jadi tidak punya expiry time.
4. Jika whitelistIps kosong:
   - semua IP boleh, kecuali diblok oleh blacklist
5. Jika whitelistIps berisi data:
   - hanya IP yang ada di whitelist yang boleh
6. Jika blacklistIps mengandung IP request:
   - selalu tolak
7. Setiap request valid harus meng-update:
   - lastUsedAt
   - lastUsedIp
   - useCount = useCount + 1

Prioritas rule:
- blacklist menang atas whitelist

IP client harus dideteksi dari header berikut, berurutan:
- x-forwarded-for (pakai IP pertama)
- cf-connecting-ip
- x-real-ip
- true-client-ip
- forwarded

Response kalau API key invalid:
- HTTP 401 Unauthorized
- JSON error yang jelas

Contoh:
{
  "error": "invalid api key"
}

Atau:
{
  "error": "ip not allowed"
}

9. FETCH MESSAGES: SUMBER DATA DAN LOGIC
================================================================================

Endpoint:
GET /api/messages/:email/:apikey

INI BAGIAN PALING PENTING.

Service Go harus membaca inbox message langsung dari storage internal:

1. Redis list:
   inbox:{email}

2. Redis string:
   message_file:{message_id}

3. Fallback file search:
   EMAIL_STORAGE_DIR recursively

Email wajib dinormalisasi:
- trim
- lowercase

Redis list yang dipakai:
- LRANGE inbox:{email} 0 {INBOX_MAX_MESSAGES-1}

Default:
- 0..19 jika env tidak ada

Setiap item list adalah JSON summary.
Minimal field yang harus dibaca:
- id
- from
- subject
- timestamp
- is_otp
- otp

Jika summary lama belum punya field is_otp atau otp:
- baca detail file message
- ambil field is_otp dan otp dari detail
- merge hasilnya

Struct yang disarankan:

type rawInboxMessage struct {
    ID        string  `json:"id"`
    From      string  `json:"from"`
    Subject   string  `json:"subject"`
    Timestamp int64   `json:"timestamp"`
    IsOTP     *bool   `json:"is_otp"`
    OTP       *string `json:"otp"`
}

type InboxMessage struct {
    ID        string  `json:"id"`
    From      string  `json:"from"`
    Subject   string  `json:"subject"`
    Timestamp int64   `json:"timestamp"`
    IsOTP     bool    `json:"is_otp"`
    OTP       *string `json:"otp"`
}

type MessageDetail struct {
    ID        string   `json:"id"`
    From      string   `json:"from"`
    To        []string `json:"to"`
    Subject   string   `json:"subject"`
    Text      string   `json:"text"`
    HTML      string   `json:"html"`
    Raw       string   `json:"raw"`
    CreatedAt int64    `json:"created_at"`
    IsOTP     bool     `json:"is_otp"`
    OTP       *string  `json:"otp"`
}

Response minimal:
{
  "email": "abc@example.com",
  "messages": [
    {
      "id": "uuid",
      "from": "Service <no-reply@example.com>",
      "subject": "Your verification code",
      "timestamp": 1710000000000,
      "is_otp": true,
      "otp": "123456"
    }
  ]
}

Urutan:
- terbaru di depan

Jangan bikin polling di server untuk endpoint ini.
Endpoint cukup one-shot fetch.
Polling nanti dilakukan oleh client/script pemakai API bila perlu.

10. DELETE MESSAGE: IMPLEMENTASI
================================================================================

Endpoint:
DELETE /api/message/:message_id/:apikey

Yang saya inginkan:
- hapus message tertentu dengan id tersebut dari inbox storage internal

Implementasi minimal yang diterima:

1. Cari semua inbox Redis list yang mungkin berisi message summary itu.
2. Atau jika ada struktur index yang lebih efisien di backend saat ini, gunakan itu.
3. Hapus summary dari Redis list terkait.
4. Hapus detail file JSON jika ada.
5. Hapus key Redis message_file:{id} jika ada.

Jika repo existing punya mekanisme lain yang lebih benar, ikuti mekanisme yang paling aman.

Kalau delete penuh lintas semua inbox terlalu mahal, boleh implementasi pragmatis:
- scan key inbox:* secukupnya
- remove message summary matching id
- delete detail file
- delete message_file key

Response:
{
  "ok": true,
  "message_id": "uuid"
}

Jika tidak ditemukan:
{
  "ok": false,
  "error": "message not found"
}
